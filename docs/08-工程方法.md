# 08 工程方法：怎么把一个需求做成可交付的代码

这一章不是语法，是“做事的方法”。项目里踩过的坑，几乎都能归到方法问题上。

---

## 1. 一个需求的完整闭环

以「睡觉动画一抽一抽」为例：

| 步骤 | 做什么 | 本项目的例子 |
|---|---|---|
| ① 复述 | 用一句话复述用户的问题，不夹带猜测 | “打呼循环每隔几秒跳一下” |
| ② 量化 | 把“看起来”变成数字 | 逐帧灰度图算相邻帧平均差、循环接缝差 |
| ③ 判据 | 先定“怎样算好” | 接缝差 ≤ 素材自身相邻帧的差，就算看不出 |
| ④ 改 | 只改判据对应的那一处 | 换循环端点 → 不够 → 改淡入 |
| ⑤ 验证 | 用同一套度量验证 | 真机抓屏 13 秒，最大 mad 3.01 |
| ⑥ 记录 | 写进笔记与提交信息 | `_notes/PROGRESS.md` + commit body |

**跳过 ②③ 直接改，就是在猜。** 本项目在睡眠上猜错过三次：

1. 用“Z 像素数量 93 ↔ 92 相等”选循环点 → 实际位置在变，整帧差 9.8；
2. 用“两端 Z 都为 0”选 76~174 → 身体在慢慢起身，腿差 12.87；
3. 用“身体位移最小”选 76~127 → 气泡每圈都要整体消失一次。

第四次改成“逐帧量身体位移 + 穷举 2544 对端点 + 段尾淡入”，才同时满足
“身体不动 / 气泡不消失 / 接缝看不出来”。每一次都是**判据错了**，不是代码写错了。

## 2. 证据分三级

| 等级 | 例子 | 能证明什么 |
|---|---|---|
| 肉眼 | 看截图、看录屏 | 观感对不对 |
| 日志 | `FEIYU_EVENT_TRACE=1` 打事件 | 消息到没到、走了哪条分支 |
| 量化 | mad 数字、毫秒、帧数、RSS | 有没有变好、好多少 |

交付一个“修好了”的结论，至少要有两级证据，并且**量化优先**。
“应该可以”“理论上没问题”在本项目里不算交付。

### 2.1 单测、自检、探针脚本的分工

- **单测**：纯逻辑，无窗口，CI 能跑。错了立刻知道是哪个函数。
- **自检**：真窗口、真提交、真抓屏。证明 Win32 这条链没坏。
- **探针脚本**：一次性取证（抓屏算 mad、注入键盘、量 CPU）。不进仓库，结论进笔记。

一个功能通常要三种都有：

- 睡眠：单测（区间换算）+ 自检（帧号范围/回绕）+ `sleep_smooth.ps1`（真机 mad）；
- 打字：单测（计数原子）+ 自检（触发/冷却/睡着）+ `--typing-probe`（真按键）。

## 3. 测试怎么写才有价值

### 3.1 断言“必须成立的性质”，而不是“当前实现”

差：

```rust
assert_eq!(pick(), "stretch");   // 依赖随机种子，改实现就挂
```

好：

```rust
assert!(ids.contains(&pick()));  // 只要求“抽到池子里的”
```

### 3.2 每个 bug 修完补一条回归测试

- `sequential_playback_decodes_one_per_frame`：曾经每帧重解整条差分链；
- `play` 早退导致“看向一边无限循环”；
- `click_happy` 不收回导致“点一下一直重复”。

测试注释里写清“为什么会有这条”，未来的你才知道不能删。

### 3.3 边界与坏输入必须测

`NaN`、负数、无穷大、空数组、退化区间、截断文件、错误版本——
这些不是“洁癖”，是崩溃和状态机错乱的来源：

- `ignores_bogus_dt`：NaN/-5/∞ 不能把状态机搞坏；
- `degenerate_limits_do_not_panic`：窗口比工作区还大时取中点；
- `rejects_truncated_file`：截断文件必须报错。

## 4. 笔记：为什么写在 `_notes/` 而不是 `target/`

- `cargo clean` 会删掉 `target/`，笔记会一起蒸发；
- `_notes/` 在 `.gitignore` 里：它是给协作者和 AI 看的过程记录，不是交付物；
- 每次接手先读 `PROGRESS.md`（现在到哪了）和 `LESSONS.md`（踩过哪些坑）。

`PROGRESS.md` 的结构：

1. 最后更新（一句话 + 数字）；
2. 项目是什么、架构、提交历史；
3. **实测数字表**（每项写明怎么测）；
4. 素材与动画覆盖（关键事实）；
5. 待办（按优先级，已完成也保留）；
6. 已知未验证（必须靠人眼）。

`LESSONS.md` 的格式：**现象 → 原因 → 做法**。只追加，不删。

## 5. Git 习惯

- **一次提交只做一件事**：修 bug 和加功能分开；
- 提交信息中文，第一行说“做了什么”，正文写“为什么”和“证据”；
- 不擅自 `push`、不改 `git config`、不 `--force`；
- 不提交素材与笔记（`.gitignore` 已经挡住）。

一个合格的提交正文（节选）：

```
fix: 睡眠循环改成 76~174 正着播 + 段尾 6 帧淡入

## 诊断（量化）
相邻帧 mad 1.76，旧接缝 148→116 是 10.1，是自然运动的 5.7 倍。

## 改法
循环端点改为 76~174；接缝 8.45 用 6 帧淡过去。

## 证据
真机 13 秒 344 次抓屏，最大 mad 3.14；自检 63/63。
```

## 6. 性能与内存怎么量

- **CPU**：`psutil`/PowerShell 采样进程 CPU 时间增量 ÷ 墙钟；不要看任务管理器的瞬时值。
- **单帧成本**：`--bench 240` 分别报告“解码”和“提交”，优化才有靶子。
- **内存**：`Get-Process` 的 `WorkingSet64` / `PrivateMemorySize64`，采样 40 秒确认不涨。
- **隐藏态**：定时器停掉后 CPU 应为 0；如果有 0.1%，先查是不是心跳定时器。

本项目的实测：单帧 0.265ms（解码 0.191 + 提交 0.074），空闲 1.43%~1.69% 单核。
1.43% 超过了最初定的“≤1%”，如实记录，不拿 bench 数字凑——**bench 不等于真实合成成本**。

## 7. 调试：先分清“消息没到”和“到了没反应”

托盘问题排查顺序（真实经历）：

1. 进程还在不在？`Get-Process`；不在的话图标是幽灵。
2. 消息到了没？直接 `PostMessage(hwnd, 0x8001, 0, 0x0202)`。
   能唤出 → 程序侧正常，问题在“壳子有没有把点击发过来”。
3. 图标还在不在？`Shell_NotifyIconGetRect`，隐藏前后同一矩形说明没被注销。
4. 还有哪条不靠托盘的唤出路径？再启动一次 exe（单实例 → `WAKE_MESSAGE`）。
5. 最后才回到“用户到底点到了什么”。本次真相是：右键菜单根本没显示，
   “点隐藏”那一下落在鱼身上，鱼从未隐藏。

**教训**：先分层定位，再改代码。不要一上来就怀疑最复杂的那部分。

## 8. 代码审查清单

提交前自查：

- [ ] 分层有没有破？`feiyu-core` 里有没有 `windows::`？
- [ ] 每个 `unsafe` 有没有 `// SAFETY:`，说明前提是否成立？
- [ ] 失败路径有没有吞错？（`let _ =` 只用于“失败也不影响主流程”）
- [ ] 新增行为有没有单测或自检？边界值测了吗？
- [ ] 常量有没有注释说明“为什么是这个值”？
- [ ] 日志/取证开关是不是只在需要时打印？
- [ ] 有没有为了“看起来整齐”而顺手重构无关代码？（一次只做一件事）

## 9. 十条铁律（从踩坑里提炼）

1. **能用数字就别用形容词**：mad 10.1 比“有点跳”有用。
2. **先定判据再改代码**：判据错了，代码越对越错。
3. **一个 bug 一条回归测试**：否则它会回来。
4. **不冻帧、不硬切、不猜循环点**：素材的连续性比代码的方便重要。
5. **平台层之外不写 `unsafe`**：分层是编译期约束，不是口头约定。
6. **错误要在读入时暴露**：清单坏了启动就报，不要播到第 7 秒才炸。
7. **资源释放顺序要写对**：图标先换后删、DC 先恢复再删位图。
8. **测试要能在没窗口的机器上跑**：纯逻辑放 `core`。
9. **笔记写“为什么”**：代码写“怎么做”，笔记写“为什么这么做、试过什么不行”。
10. **交付要有证据**：构建、测试、自检、截图/数字，缺一不可。
